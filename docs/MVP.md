# Выгул собак и передержка — черновик MVP

## Цель

Помочь владельцу найти исполнителя для выгула или передержки собаки, оформить заявку и видеть её статус. Исполнитель видит доступные заявки, принимает подходящую и отмечает выполнение.

## Роли первой версии

- **Владелец** — добавляет собак, создаёт заявки и следит за их статусом.
- **Исполнитель** — выгульщик, ситтер или человек, который оказывает обе услуги; просматривает доступные заявки и берёт их в работу.
- **Администратор** — на старте может быть ручной операционной ролью; отдельный интерфейс пока не включён в MVP.

Подтверждено: desktop-версией пользуются владельцы и исполнители.

## Функции MVP

1. Регистрация и безопасный вход.
2. Профиль пользователя и выбор типа услуг исполнителя.
3. Карточка собаки: кличка, порода, возраст, особенности и контактная информация владельца.
4. Заявка на выгул: дата и время, длительность, адрес/район, собака и комментарий.
5. Заявка на передержку: даты начала и окончания, собака, место/район и комментарий.
6. Список доступных заявок для исполнителя; принятие одной заявки одним исполнителем.
7. Статусы заявки и история изменений.
8. Завершение услуги и заметка/отчёт для владельца.

## После MVP

- Онлайн-оплата и возвраты.
- Карты и отслеживание маршрута.
- Отзывы, рейтинги и проверка исполнителей.
- Чаты, push-уведомления и автоматические напоминания.
- Повторяющиеся прогулки, промокоды и сложные правила отмены.

## Технический набросок

- Один API и одна база данных для desktop- и mobile-клиентов.
- Текущий API: ASP.NET Core + PostgreSQL.
- API переведён на .NET 10 LTS.
- Текущий интерфейс: React + Vite; его можно развивать как веб-интерфейс и затем упаковать для desktop.
- Для мобильного приложения позже сделать мобильный интерфейс, работающий с тем же API.

## Сценарии и данные

- Заявка имеет вид услуги: **выгул** или **передержка**. Общими остаются владелец, собака, исполнитель, статус и комментарии.
- Для выгула нужны дата/время и длительность.
- Для передержки нужны дата/время начала и окончания.
- Исполнитель указывает, какие услуги оказывает; выгульщик и ситтер могут быть одним человеком.
- Запись заявки должна атомарно назначать её одному исполнителю, чтобы два исполнителя не могли принять её одновременно.
- Владелец должен видеть только свои заявки и собак; исполнитель — доступные заявки и назначенные ему заказы.

## Этапы

1. Уточнить MVP и роли.
2. Согласовать модель данных и сценарии выгул/передержка.
3. Исправить базовые API-проблемы: вход, хеширование паролей, CORS и миграции.
4. Реализовать основные экраны и связать их с API.
5. Собрать desktop-версию.
6. Сделать мобильный клиент на той же серверной основе.
7. Подготовить изменения API и фронтенда к публикации в соответствующих GitHub-репозиториях.

## Ближайший технический этап

Основу входа и разграничения доступа добавили. Следующий шаг — применить новые миграции к локальной базе и пройти сценарии входа, профиля собаки и заказа. Оплату пока считаем внешней договорённостью между сторонами; встроенную оплату оставляем после MVP.

## Текущий статус

- Подтверждено: desktop-версией пользуются владельцы и исполнители.
- Установлен .NET SDK 10.0.404; API переведён с .NET 9 на .NET 10.
- В API и модели данных добавлены тип услуги, начало и окончание заказа, длительность выгула.
- Добавлены миграции для передержки, недостающего отчёта и пользовательских сессий. Миграции ещё не применялись к базе данных.
- Регистрация хеширует пароль; вход создаёт истекающую bearer-сессию, в базе хранится только её хеш. Пароли тестовых пользователей из старого прототипа перехешируются при первом успешном входе.
- Доступ к собакам и заказам ограничен ролью и владельцем; фронтенд прикрепляет токен к API-запросам.
- API собирается на .NET 10 без ошибок и предупреждений.
- Сборку фронтенда пока не запускал: в папке нет node_modules.

Перед использованием API нужно применить миграции к базе. Далее завершим экраны владельца и исполнителя, затем упакуем desktop-версию и подготовим мобильный клиент. Отдельно проверим оба GitHub-репозитория и опубликуем изменения в них.
